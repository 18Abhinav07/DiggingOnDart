Prefill Stutter Report
Application · SDE-1 · Dart Browser

Local inference makes GPU-heavy pages stutter. Here is the measurement, and the scheduler I'd build.

I reran the performance claims of DBR-2026-05 and DBR-2025-01 on a fifth machine and added the measurement neither paper has: what the browser feels like while the model runs. On a GPU-heavy page, prefill at llama.cpp's default batch drops up to 83% of frames. A fixed small batch fixes 7B but not 14B, and it slows down pages that were already smooth. Stage 2 is a frame-aware prefill scheduler.

Finding 1

The stutter is real, on third-party pages, and only during prefill

Each page was calibrated to idle at 120 fps with no model loaded. A frame counts as dropped when its interval exceeds 1.5× the page's own idle median (8.3 ms here). The model is Qwen 2.5 7B Q4_K_M prefilling a 4,000-token page, with Brave in front.

ubatch 512 (llama.cpp default)ubatch 64
The default is fine on light pages and BBC News, and drops 30–83% of frames on GPU-heavy ones. Decode drops nothing on any GPU-heavy page. CPU-only prefill keeps the shader page at 0.1% but takes 104 s instead of 11.5 s, so the cause is GPU contention.

MotionMark Multiply, a CPU-bound DOM test, is the exception. It drops 4% at idle and about 9.5% in decode at every GPU setting. Finding 4 follows that up.

Finding 2

The size of each GPU submission is what matters. Pauses between submissions don't help.

I tried every mitigation that works without touching the browser. Gaps between 128-token chunks don't help, because each chunk is still one long GPU submission. At 64 tokens it is smooth with or without a gap. Cutting the chunk size per request works, but it costs about twice the TTFT of setting the size inside the runtime.

ubatch, fixed when the model loadspaced chunks, one request each (c = tokens, g = gap ms)
7B on the shader page. Bottom-left is best. ubatch 64 is the cheapest smooth point (+11% TTFT). Per-request chunking gets there at +23% (c64, no gap). CPU-only, at 104 s and 0.1%, is off the chart.
Finding 3

No single fixed setting works for every model

ubatch 512ubatch 64
Shader page. ubatch 64 makes 3B and 7B smooth but not 14B. A fixed value safe for 14B would be 32 or less, and ubatch 32 costs 7B about 17% TTFT on every page, including pages that never needed it.

This is the case for a scheduler over a constant. A constant small enough for the heaviest model on the weakest Mac taxes every other combination all the time. On BBC News the default is already smooth, and a fixed 64 adds 5.5% TTFT there for nothing. A controller only pays that cost while a GPU-heavy page is in front.

Finding 4

A second engine agrees. Moving inference to the CPU is worse, not safer.

Two follow-ups, both with 7B Q4 prefilling 4,000 tokens. Safari (WebKit) ran the same shader page. Safari renders at 60 Hz here, so its budget is 17 ms and it has half as many deadlines to miss as Brave at 120 Hz. CPU-only inference (-ngl 0) ran against MotionMark Multiply, a page bound by the main thread rather than the GPU.

WebKit shows the same mechanism: prefill drops frames, decode doesn't, and a 64-token batch removes the drops. The CPU result changes the design. CPU inference competes with the page's main thread in both phases, and halving the threads still leaves 18% dropped while adding 46% to TTFT. That fits DBT-2026-09's cap of 12% of a core for background embedding. So "fall back to CPU" isn't a mitigation. The scheduler needs a CPU budget alongside the GPU one.

Proposal

Stage 2: a frame-aware prefill scheduler

This is a component between the browser and the local runtime. It decides how many tokens each prefill step submits to the GPU, based on whether the frontmost tab is meeting its frame deadlines.

  1. Knob: tokens per llama_decode call

    Embedded in-process, the caller chooses k for each step, so no model reload is needed. llama-server can't do this because ubatch is fixed when the model loads. The first measurement is whether in-process chunking closes the gap between +23% (per-request) and +11% (ubatch 64).

  2. Signal: missed frame deadlines in the visible tab

    In the product this comes from compositor presentation feedback. In the prototype it comes from the rAF recorder this harness already injects over DevTools, read in 250 ms windows.

  3. Controller: AIMD on k

    k starts at the ceiling. It halves when a window drops more than the page's idle rate and grows additively while frames stay clean. The floor and ceiling come from a per-device, per-model table measured by this harness. On this M4 Pro the floor is 64 for 3B and 7B and below 64 for 14B. The ceiling is 1024, because ubatch 2048 drops 2.9% even on the light page.

  4. Policy: leave decode and hidden tabs alone

    Only the frontmost visible tab counts. GPU decode is never throttled because it never caused drops on GPU-heavy pages. When the window is hidden, prefill runs at the ceiling. Work that has to use CPU cores, such as embedding or CPU fallback, gets a thread budget from the same signal, never llama.cpp's default of every performance core.

Deliverables

  • dartsched: a small C++ library over llama.cpp with chunked prefill, the controller, a pluggable frame signal and the device/model table.
  • A frame-signal prototype feeding the controller over a local socket. Where the production hook goes in Dart's compositor is Dart's call.
  • This harness as the regression suite (light, shader, Aquarium, MotionMark, BBC) with a CI quick mode.
  • A report comparing static 512, static 64 and the scheduler on at least two Macs, one of them a base M-series.

Success criteria, fixed before building

smoothOn every GPU-heavy page, prefill drops ≤ 2 points above idle, for 3B, 7B and 14B
freeOn light pages, TTFT within 2% of ubatch 512
cheapOn heavy pages, TTFT no worse than the smallest fixed ubatch that is smooth for that model
fastWhen a heavy page comes to the front mid-prefill, drops recover within 500 ms
fallbackIf in-process chunking costs as much as the HTTP version, say so and switch between two or three preloaded contexts instead

What the rerun says about the papers' limits

  • The 640 ms TTFT only fits a cached prefix. 7B at 4k is 11.4 s cold and 79 ms when the page is already in the KV cache (3B: 5.1 s vs 45 ms; 14B: 23.7 s vs 159 ms). No model tested gets a cold 4k prefill under 900 ms on this machine. Decode and memory limits pass easily.
  • No 2.3× swap cliff on 24 GB. 18 GB of other memory slows 7B decode by 6%. Swapping starts between 8 and 14 GB of ballast.
  • Low-bit quants save memory, not speed. Q8_0 prefills faster than Q2_K (410 vs 374 tok/s at pp512) on this GPU.
  • Not rerun: accuracy, because it needs Dart's 640-item set. Speculative decoding (E3) and energy (E6) weren't run either. E6 needs root for powermetrics.

Limits

  • One machine. Brave stands in for Dart, since both are Chromium. Safari is the second engine, at 60 Hz rather than 120 Hz. Qwen 2.5 on llama.cpp 0.7.0, while Dart used b4021. rAF intervals are a proxy for compositor frames.
  • The decision rule was amended after seeing data. As written before E4, it read only the light page and said "build the capability gate". I changed it to "worst page decides" once the heavy page showed 64% drops. Both verdicts are printed in the report.
  • One 4-minute condition ran while something outside the benchmark halved the machine's decode speed. It is kept and labelled "disturbed", and I reran it.
